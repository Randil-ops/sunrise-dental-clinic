01

Test Rationale

The system's value sits almost entirely in AppointmentService — it is the one class that enforces every business rule the clinic depends on (no double-booking, valid contact numbers, no past-dated or out-of-hours appointments, correct bill totals). Controllers and repositories are thin by comparison: Spring Data JPA generates the repository implementations, and the controllers only translate HTTP requests into service calls. Testing effort was therefore concentrated where the risk actually is — the service layer — with a smaller set of tests confirming the REST layer wires up correctly and the Spring context itself boots without configuration errors.

Each service test targets exactly one business rule and asserts one outcome, so a failing test immediately identifies which rule broke, rather than requiring the developer to re-derive it from a generic "something is wrong" failure.

Test isolation

Every service-layer test is annotated @Transactional, so each test's writes are rolled back automatically at the end of the test method. This means the shared file-based H2 database used by the running application is never permanently polluted by test data, and tests do not interfere with one another regardless of execution order.

03

Test-Driven Development in This Project

Test case 5 above (clinic operating hours) was built using a genuine red–green TDD cycle, run live during development, to demonstrate the practice rather than just describe it:

1 · Red

The test registerAppointment_rejectsAppointmentOutsideClinicOperatingHours was written first, asserting that booking an appointment at 20:00 throws ValidationException. At this point AppointmentService.validate() had no such check. Running mvn test produced exactly one failure, with the message "Expected ValidationException to be thrown, but nothing was thrown." — confirming the test correctly detects the missing behaviour.

2 · Green

Two constants (CLINIC_OPENING_TIME = 08:00, CLINIC_CLOSING_TIME = 18:00) and one guard clause were added to validate() — the minimum code needed to satisfy the assertion. Re-running the full suite produced 8/8 passing, with no other test affected, confirming the fix was both correct and non-regressive.

No further refactor step was needed here: the guard clause follows the exact same shape as the five validation checks already in validate(), so introducing it did not create duplication or reveal a better structure to extract.

Why only this one rule was built test-first

The other seven tests were written to characterise behaviour that already existed from earlier implementation work (registration, billing, the REST layer), so they function as a regression safety net rather than a red–green demonstration — which is an equally valid and common use of automated tests, just not literal TDD. The operating-hours rule was deliberately introduced test-first specifically to produce an honest, reproducible record of the TDD cycle for this document, rather than presenting it as if the whole codebase had been built rule-by-rule from a blank test file, which would not accurately describe how the project was actually developed.
