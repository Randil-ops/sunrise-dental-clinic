01

Use Case Diagram

The clinic has a single actor in the current scope: Staff (receptionist/dentist administrator), matching the brief's requirement that "only authorized staff can use the system." All seven functional requirements from the scenario map directly onto use cases below.

Assumptions

No separate "Patient" actor was modelled, since the scenario describes staff entering patient details on their behalf (a walk-in/phone-booking clinic workflow), not patient self-service.

A single "Staff" role was assumed rather than distinct Receptionist/Dentist roles, since the brief does not require differentiated permissions — this is documented here as a deliberate scope decision rather than an oversight.

Design rationale: "Validate Patient Input" and "Check Dentist Double-Booking" are modelled as <<include>> because AppointmentService.registerAppointment() always performs both steps — they are not optional. "Print Receipt" is <<extend>> because printing is a UI-triggered optional action after a bill has already been generated, not a mandatory part of billing.

02

Class Diagram

The class diagram reflects the actual layered architecture: web controllers depend on a single service facade, which coordinates two repositories and a billing strategy. Visibility modifiers mirror the real source — all entity fields are private with public accessors, consistent with encapsulation.

Assumptions

Appointment and StaffUser have no direct association in the domain model (no "booked by" foreign key) — the brief does not require attributing an appointment to the staff member who created it, so this was left out of scope.

Sequence Diagrams

Three representative flows are modelled below, covering authentication, the core write path (registration, including its validation and conflict-checking branches), and the core read/compute path (billing).

3.1 — Staff Login

sequenceDiagram
    actor Staff
    participant AuthController
    participant AppointmentService
    participant StaffUserRepository
    participant DB as H2 Database

    Staff->>AuthController: POST /login (username, password)
    AuthController->>AppointmentService: login(username, password)
    AppointmentService->>StaffUserRepository: findByUsername(username)
    StaffUserRepository->>DB: SELECT * FROM staff_user WHERE username = ?
    DB-->>StaffUserRepository: StaffUser row
    StaffUserRepository-->>AppointmentService: Optional<StaffUser>
    alt password matches
        AppointmentService-->>AuthController: Optional.of(user)
        AuthController-->>Staff: redirect /home (session set)
    else invalid credentials
        AppointmentService-->>AuthController: Optional.empty()
        AuthController-->>Staff: re-render login (error message)
    end

3.2 — Register New Appointment

sequenceDiagram
    actor Staff
    participant ClinicController
    participant AppointmentService
    participant AppointmentRepository
    participant DB as H2 Database

    Staff->>ClinicController: POST /appointments/new (form data)
    ClinicController->>AppointmentService: registerAppointment(appointment)
    AppointmentService->>AppointmentService: validate(appointment)
    alt validation fails
        AppointmentService-->>ClinicController: throws ValidationException
        ClinicController-->>Staff: re-render form (error message)
    else validation passes
        AppointmentService->>AppointmentRepository: existsByDentistNameAndAppointmentDateAndAppointmentTime()
        AppointmentRepository->>DB: SELECT COUNT(*) ...
        DB-->>AppointmentRepository: count
        alt clash found
            AppointmentRepository-->>AppointmentService: true
            AppointmentService-->>ClinicController: throws DoubleBookingException
            ClinicController-->>Staff: re-render form (error message)
        else no clash
            AppointmentRepository-->>AppointmentService: false
            AppointmentService->>AppointmentService: generateNextAppointmentNumber()
            AppointmentService->>AppointmentRepository: save(appointment)
            AppointmentRepository->>DB: INSERT INTO appointment ...
            DB-->>AppointmentRepository: saved row
            AppointmentRepository-->>AppointmentService: Appointment
            AppointmentService-->>ClinicController: Appointment (with appointmentNo)
            ClinicController-->>Staff: success message + appointment number
        end
    end

3.3 — Calculate and Print Bill

sequenceDiagram
    actor Staff
    participant ClinicController
    participant AppointmentService
    participant AppointmentRepository
    participant BillingStrategy as StandardBillingStrategy
    participant TreatmentPricingConfig

    Staff->>ClinicController: POST /bill (appointmentNo)
    ClinicController->>AppointmentService: generateBill(appointmentNo)
    AppointmentService->>AppointmentRepository: findByAppointmentNo(appointmentNo)
    alt not found
        AppointmentRepository-->>AppointmentService: Optional.empty()
        AppointmentService-->>ClinicController: throws AppointmentNotFoundException
        ClinicController-->>Staff: "No appointment found" message
    else found
        AppointmentRepository-->>AppointmentService: Appointment
        AppointmentService->>BillingStrategy: calculateTotal(treatmentType)
        BillingStrategy->>TreatmentPricingConfig: getPriceFor(treatmentType)
        TreatmentPricingConfig-->>BillingStrategy: treatment price
        BillingStrategy-->>AppointmentService: consultationFee + treatmentPrice
        AppointmentService->>AppointmentRepository: save(appointment) [billed=true]
        AppointmentRepository-->>AppointmentService: updated Appointment
        AppointmentService-->>ClinicController: Appointment (with totalCost)
        ClinicController-->>Staff: printable receipt
    end

Design Patterns Reflected in the Diagrams

FACADE

AppointmentService is the single entry point for all three controller types (Thymeleaf, Auth, REST), hiding repository and billing coordination behind one API.

STRATEGY

BillingStrategy / StandardBillingStrategy lets the billing rule be swapped without touching AppointmentService.

REPOSITORY / DAO

AppointmentRepository and StaffUserRepository isolate persistence concerns from business logic (Spring Data JPA implementation).

SINGLETON

TreatmentPricingConfig is a Spring-managed singleton bean — one shared price table for the whole application.

◆

Evaluation

Modelling the use cases first surfaced the two mandatory sub-behaviours of registration (validation and double-booking checks) that the brief only implies rather than states, which in turn justified introducing dedicated exception types (ValidationException, DoubleBookingException) rather than a single generic error path — the sequence diagrams show these as distinct alt branches, which made the corresponding JUnit test cases (one per branch) straightforward to derive directly from the diagram.

The main trade-off in the class diagram is that AppointmentService is a fairly wide facade (six public operations). This was judged acceptable at this scale — splitting it into, say, a separate BillingService would add indirection without a corresponding gain in clarity for a system with only two entities, but it is flagged here as the first extension point if the system grows (e.g. adding invoicing history or multi-branch support).
